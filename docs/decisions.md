# Decisions

Closed decisions only. Open items are in `project_plan.md`. Last updated: 26/11/2026.

| # | Decision | Reason (rejected alternative) | Source |
|---|---|---|---|
| D1 | Attendance counts only students physically in class. Zoom students are not counted. | The assignment defines F1 as attendance "in class". Rejected: a remote-attendance path. | Assignment |
| D2 | A class photo is used only to count people. No face recognition. A count gap alerts and never blocks. | Face recognition makes discriminatory errors and carries a regulatory burden. | Lecturer (lecture) |
| D3 | No integration with Moodle, Zoom or university systems. Files are uploaded manually. | The assignment says no need to integrate. | Assignment |
| D4 | Students use a mobile web app, with no installation. | KISS requirement. | Assignment |
| D5 | Real personal data never enters the repo. It stays in git-ignored `private_data/`. Tests use synthetic data. | Public repo, privacy. | Own decision |
| D6 | All five features are implemented, in order F1 to F5. F1 in depth; F4 and F5 thin slices. | F1 is the main feature. | Assignment, own decision |
| D7 | Two QR codes: a fixed one for the class page (comments, polls) and a rotating one (5-10 s) for attendance only. | Rotation stops a photo of the code being forwarded. For comments it only adds friction. | Own decision |
| D8 | Identity by Google sign-in; the Google account email must match the roster email. The roster is the Moodle export; only name and email are read. A student not on the roster cannot register; the lecturer adds or edits the entry. A device is registered once, then scan and one tap. No ID numbers are stored. | Nobody can mark for a friend just by knowing a number. Rejected: typed ID or name. Subject to spike S1. | Lecturer's idea |
| D9 | Presence is checked by location only (about 50 m from the building). Only a yes/no result is stored. There is no check of the network (IP). | A deterrent, not proof. Rejected: a campus-network check, because most students use mobile data and would be flagged for nothing. Block or flag: see plan (S3). | Own decision, 18/11 |
| D10 | F2: anonymous free-text comments, shown live on the lecturer page (auto-refresh) in the same app. No categories. Students see only their own. Kept until the end of the semester; the lecturer can hide or delete. | Shy students take part more; KISS. | Own decision |
| D11 | F3: the lecturer creates a poll during class (question, 2-4 options, optional correct answer) and closes it. Students refresh the class page to see it; no automatic check. After closing, each student sees right or wrong, and the lecturer sees the number of votes per option (can project it). Anonymous, one vote per browser, no cheat protection. Results kept to semester end; the lecturer can delete. | The simplest poll that supports comprehension questions. | Lecturer (lecture), own decision |
| D12 | F4: input is a Zoom transcript (VTT preferred) or, if none, a recording (audio extracted, split, transcribed). Output: short summary, chapters with timestamps, keywords, a "related to" line (from this transcript only), date and length; copy or download. An existing LLM API; the uploaded file is deleted after processing. S5 compares it with Zoom's own summary. | Reuse existing tools. Rejected: our own model, relating to the whole syllabus. | Lecturer (lecture), own decision |
| D13 | F5: a critical report, no grade, no rubric, made by the system with no human in the loop. Layer 1: repo accessible, checklist items found, links ("cannot verify" for private shares). Layer 2: an LLM rates fixed topics per README (absent, brief, detailed); the class comparison is counting in code; a few remarks. No sign-in for students; abuse is limited by a per-browser delay, a daily cap and a provider spending limit. The student report is not stored; the lecturer overview is kept to semester end. No similarity check; others' code is not run. | The lecturer rejected a rubric. Running others' code needs a sandbox. | Lecturer (lecture) |
| D14 | Lecturer pages are protected by one password in an environment variable (`.env` locally, never committed). | KISS, minimal friction. | Own decision |
| D15 | Bluetooth proximity is rejected. | A phone browser cannot do it (not on iPhone). | Lecture analysis |
| D16 | A student may register several devices, each by Google sign-in. In one session a device can mark only one student: a second attempt is blocked and flagged for the lecturer. A new device for an already registered student is also flagged. Flags are shown to the lecturer only, and matter only when the count gap alert (D18) fires. | The honest student is not burdened. The cookie block is soft (cleared cookies or a private window bypass it), so the photo count is the safety net. | Own decision, 18/11 |
| D17 | Prefer existing tools and libraries; build only the glue (for example ffmpeg, an LLM API, the Zoom transcript). | The assignment prefers other code; limited time. | Assignment, own decision |
| D18 | If the marks exceed the photo count by more than 5% (initial value, calibrated in S4), the system alerts the lecturer. If some marks are flagged, the lecturer checks only those students (for example by calling the names) and can mark an entry "unverified". If no mark is flagged, the list stands. No new round and no automatic penalty. | A second scan round does not stop a multi-device cheater. The photo count shows only an aggregate gap. The honest student is not disturbed. | Own decision, 18/11 |
| D19 | The lecturer taps Start class, which creates today's session if none exists yet. A closed window still asks about a new session (unchanged): if attendance is opened in a session that already has a closed window, the system asks whether to start a new session (for example a tutorial) and its name (1b, D31). Attendance, comments and polls belong to today's session; with no session today, student pages say "Class has not started". Assumption: a class takes place on its date (no postponed classes). | KISS: lecture and tutorial on one day stay separate with one tap; comments and polls during class need a session before attendance opens. Rejected for now: a timetable (future improvement); creating the session automatically from the date. | Own decision, 18/11; simplified 20/11; changed 21/11 |
| D20 | IDs for all project documents are a flat two-digit sequence per type, like `UC-nn`: `FR-nn`, `NFR-nn`, `TC-nn` (tests), `C-nn` (components), `R-nn` (risks). Spikes stay `S1-S6`, decisions `Dn`. Parameters have a constant name (for example `ATT_WINDOW_SEC`) used identically in every document. An ID is never reused; a removed item is marked "retired". The feature (F1-F5) goes in a separate column. | Consistent with `UC-nn`; numbers do not shift while features are written one at a time. Rejected: `FR-F1-01` (longer, differs from `UC-nn`); `FR-1.01` (inconsistent with `UC-nn`). | Own decision, 18/11 |
| D21 | Data retention, one rule. Everything stored (roster, device links, sessions, attendance rows, count and gap, comments, polls, F4 summaries, F5 overview) is kept until the end of the semester, then deleted. Uploaded files (class photo, transcript or recording, submissions list) are deleted after processing. The F5 student report is not stored. F5 limit counters reset daily. Two exceptions are kept until the lecturer changes them: the F5 checklist and the class location (D28). | Privacy (keep the minimum); attendance is the product and is needed through the semester; one simple rule (KISS). Rejected: deleting attendance after each class (it is the deliverable); keeping data with no end date (privacy); a different period per item (complex). | Own decision, 18/11 (Claude proposed, approved) |
| D22 | The user interface is in English. F4 summaries and F5 reports are written in the language of the input (transcript or README). | One UI language (KISS); lectures and READMEs may be in Hebrew. | Own decision, 18/11 |
| D23 | Stack and host: Python 3.13, FastAPI, one uvicorn worker, plain `sqlite3`, Jinja2. Railway Hobby (always-on, SQLite on a Volume), hard usage limit $10 (raise if S4 needs more RAM). | S1 worked end to end. Rejected: serverless + hosted DB, ORM, frontend framework, Railway Trial. | Own decision, 21/11; plan 22/11. Reuses the S1 service and URL; Hobby before the S2 load check (26/11 at the latest). |
| D24 | Every data-changing action is a POST; no GET writes to the database. The Google sign-in callback (a GET) only verifies the sign-in and keeps the email in the signed session cookie; a "Confirm registration" POST writes the device link. | In S1 a GET that wrote data added duplicate rows. Rejected: an exception for the callback. | Own decision, 21/11; S1 |
| D25 | F4 and F5 background jobs are a row in one `jobs` table plus a thread in the same process. At most one running job per kind. A job left "running" by an earlier server run (another boot id) is shown as failed. | Tested in S1; no extra service. Rejected: a queue system (Celery, Redis), synchronous jobs. | Own decision, 21/11; S1 |
| D26 | Lecturer access: one signed session cookie that lasts 8 hours; a logout button on every lecturer page. After 5 wrong passwords, login is locked for 300 s for everyone. The counter is in memory only and resets on restart. | KISS (D14). Rejected: the counter in the database, per-IP limits. A lockout also blocks the real lecturer until it ends (accepted). | Own decision, 21/11 |
| D27 | Student browsers get two separate random cookies, each for 120 days: a device cookie (linked to the roster entry after Google sign-in, F1) and an anonymous id (comments, polls, F5 limits). The anonymous id is never stored with the device id or a roster entry. A cleared device cookie means signing in again and a "new device" flag (D16). | One semester with one sign-in; comments and answers stay anonymous (D10, D11). The 120-day lifetime is not verified. | Own decision, 21/11 |
| D28 | The lecturer sets the class location in the app, on the Start class page: "Use my current location" or a "lat, lon" pasted from Google Maps. It is stored in the database and kept until the lecturer changes it. If none is set, the location check is skipped and the lecturer page warns (proposal, to confirm in S3). | A place, not personal data; no code change when the room changes. Rejected: environment variables for the location. Laptop location may be inaccurate (check in S3). | Own decision, 21/11 |
| D29 | Code layout: one `app/` package with one module per component (for example `roster.py`, `attendance.py`); tests in `tests/`; classes as in the EDD. | KISS, 4 days left. Rejected: one package per component (more files). | Own decision, 22/11 |
| D30 | Roster input is a CSV file (UTF-8), read by header name: first name, last name, email (`שם פרטי`, `שם משפחה`, `דוא"ל`). Other columns, such as the class group number, are ignored. | No extra library; matches FR-01, D8 and UC-00. Rejected: XLSX or Google Sheet as input; using the groups column. | Own decision, 22/11 |
| D31 | UC-01 1b is built: after a closed or expired window, the lecturer can start a new session for today (optional name); the old session and its marks stay. "Open attendance" on a closed window still shows "Attendance already closed for this session". | No recovery otherwise (testing, rehearsal, demo). Rejected: reopening the same session; no auto-expiry. | Me, 24/11 (deferred); 25/11 (built) |
| D32 | Roster re-upload: match by email; entries missing from the new file become inactive but are kept, so old marks keep their name; an inactive entry returns when the same email is added again. | Keeps attendance history. Rejected: deleting them. | Own decision, 24/11 |
| D33 | No manual head count: only the app counts the class photo (S4); if counting fails, an error is shown and no count is stored. | The app should save the lecturer the counting; the QR and location layers remain. Rejected: a typed count (UC-04 2a). | Me, 26/11 |
| D34 | The review lists flagged marks first and highlighted, always; flags of students with no mark are shown in one line. The lecturer sees flags always and acts on them only when the gap alert fires (D16). | Step 7 has no count, so the lecturer sees all flags. Rejected: a flagged-only filter (for now). | Me, 26/11 |
| D35 | Optional (Could) F2/F3 flows appear in the STP B11 table as "Could (srs App. C), not built". | Keeps B11 complete without building them. Rejected: building them; editing B11 in srs. | Me, 26/11 |
| D36 | While a poll is open the lecturer page shows only the number of answers; votes per option, the correct answer and right/wrong appear after Close. The server sends no per-option counts while open. | A projected page would influence the answers. Rejected: live counts per option (UC-08 s3 before); hiding them only in the page. | Me, 26/11 |
| D37 | Head count (S4): YOLOX-s (OpenCV Zoo, ONNX) with OpenCV on our server, the full photo plus 3x2 overlapping tiles merged by our own code; GAP_TOLERANCE_PCT stays 5. | 11 photos on a laptop: all within 10%, mean absolute error 3.5%. Rejected: no tiling (7 of 11), supervision and sahi (heavy dependencies). YOLOX-m not tried (101 MB). | Me, 27/11, from the S4 spike |
| D38 | A second photo of a session replaces the stored count. | A blurry photo can be retaken. Rejected: refusing a second photo; keeping a history. | Me, 27/11 |
